# Academic PPT Workflow 中文操作说明书

当前文档对应工作树中的 assisted workflow；本次整合属于 **UNRELEASED / NEXT**。
现有版本元数据统一为 `2.7.0-rc4`（Python 写法 `2.7.0rc4`），不代表发布了新版本。

## 1. 系统定位与边界

系统把有来源的科学内容转成可编辑 PowerPoint，保留来源、声明、备注、图表数据和审核记录。
它可以检查科学绑定、文件完整性、实际文字几何和视觉流程是否完整；不能保证每份 PPT 都美观，
不能替作者决定科学解释、图表科学内容或最终结论。缺失信息显示 `INFORMATION_REQUIRED`。

## 2. Windows 安装与环境变量

需要 Python 3.12、Node.js 20 或以上、已安装的 Microsoft PowerPoint。不要安装额外字体来掩盖排版问题。
Master 当前允许 Arial、Microsoft YaHei。PowerPoint 不可用时，Windows 最终验证不能视为通过。
在解压后的仓库根目录运行以下命令；工作区与应用目录分开：

```powershell
$env:PPT_WORKFLOW_HOME = (Get-Location).Path
$env:PPT_WORKSPACE_HOME = Join-Path (Split-Path $env:PPT_WORKFLOW_HOME -Parent) 'academic-ppt-workspace'
& .\scripts\bootstrap_windows.ps1 -WorkflowHome $env:PPT_WORKFLOW_HOME -WorkspaceHome $env:PPT_WORKSPACE_HOME
& .\scripts\doctor.ps1 -WorkflowHome $env:PPT_WORKFLOW_HOME -WorkspaceHome $env:PPT_WORKSPACE_HOME
```

bootstrap 只在应用 `.venv` 与 `node_modules` 安装锁定依赖，不修改全局 Python/Node 包。
依赖安装可能联网；图像管线没有网络生成、API 或密钥处理。
本地 `config/local.yaml` 不进入 Git。路径优先级：命令参数、环境变量、本地配置、默认值。
可另设 `PPT_CACHE_HOME`；临床缓存必须留在获准的私有本地位置。

## 3. 项目目录

```text
<workspace>/projects/<project>/
  input/                    原始资料，只读
  brief/presentation_brief.yaml
  brief/visual_brief.yaml
  brief/visual_plan.json     科学处理之后准备的独立视觉计划
  approved_assets/           人工批准的装饰资产
  output/<run>/draft/        草稿与待审核 Deck
  output/<run>/final/        仅已满足交付门禁的 Deck
  output/<run>/preview/      联系表
  staging/                  完整处理中间文件
  audit/                    QA、来源与人工复核证据
```

实际运行目录以命令输出和 `project_interface` 的 run contract 为准，不把项目文件放回应用仓库。

## 4. 四条路线

| 路线 | 输入与行为 |
|---|---|
| `generate` | 来源资料生成新的原生 Deck |
| `enhance` | 对已有 Deck 执行有边界的更新，保留 KEEP 页 |
| `template-fill` | 在获准机构模板内填入新内容 |
| `template-create` | 提取样式 profile；不是生成科学 Deck |

## 5. 三种质量模式

| 模式 | 实际行为 |
|---|---|
| `quick` | 草稿；生成路线仍保留来源检查，enhance 可用增量路径；不认证 Floor |
| `validated` | 完整科学 QA、实际渲染、Floor、页面角色、组合/插图决策、Master、联系表和人工门禁 |
| `full` | validated 加入完整 OOXML/隐私审计、验证过的来源文件哈希记录、Ambition 和 Anchor/STRETCH 机会复核 |

Floor 的输出是 BLOCK、WARN 或 HUMAN_REVIEW 等过程状态，不是审美分数。
自动 QA 通过不能代替 Human Gate。待复核文件保留在 draft；`BLOCK` 返回非零退出码。

## 6. 输入与科学来源

原始文件只读，来源 manifest 记录 SHA256。科学 claim、数字、图和引文必须有 source binding。
`SCIENTIFIC_SOURCE`、`PRESENTATION_BASELINE`、`STYLE_REFERENCE`、`FORMAL_TEMPLATE` 和装饰资产承担不同角色。
既有 PPT 默认是 presentation baseline，不能自动充当科学证据；继承而未重验的内容需要人工复核。
图片生成结果不能进入科学来源注册表。OCR 默认不执行；不要将没有读取的图片内容当作已核验事实。

## 7. presentation_brief

记录主题、受众、时长、语言、路线、质量模式、来源规则、隐私限制和已有 Deck/模板。
创建项目会写入模板。补齐 `INFORMATION_REQUIRED`；不要把缺失的方法、结果或参考文献交给程序猜测。
Brief 改变会影响缓存有效性。研究定义的修改必须由 Scientific Owner 决定。

## 8. visual_brief 与 Human Gate

visual_brief 只管理呈现方向：字体角色、颜色、密度、插图强度、视觉层次等。
其 `approval.status` 必须是 `approved` 才可作为执行依据；批准人和日期由人填写。
此批准不批准科学内容，也不批准尚未出现的图像候选。
模板优先级高于普通呈现方向，不能用 style-only 参考中的内容补充科学证据。

## 9. 页面角色与 semantic composition

科学规划产出 Deck IR 后，在首次 validated/full 完整处理生成的 `visual_evidence/visual_plan_template.json` 上准备视觉计划，
保存为项目 `brief/visual_plan.json`。模板的审批为空，角色不明确时也为空。
计划须包含 `assisted-visual-plan/1`、IR 的 `canonical_hash`、完整顺序的 slide ID/index 和明确角色。
每页记录语义映射、组合 family、插图决定和必要的 fallback 理由/被排除方案。

可选 `semantic_composition` 只改变源文本和图关系的原生排布，节点、边、顺序与标签必须严格一致。
它仅用于 generate。科学图、表和既有用户对象不能被任意改绘。
计划中的 family 声明不是渲染证明；原生组合执行记录或逐页实际观察证据仍是必需的。

## 10. Master/Layout

系统创建真实 OOXML Master、Custom Layout 和 theme parts，保留原 Deck 中其他部件。
七种布局是 HERO_SCENE、CONTEXT_EDITORIAL、EVIDENCE_CLEAN、FRAMEWORK_EDITORIAL、
IMPLEMENTATION_EDITORIAL、TIMELINE_CONTINUUM、CLOSING_EDITORIAL。
标题、来源、页码使用可行的原生占位符继承；科学内容仍位于 slide 实例。
默认是无图的克制主题，不能自动借用其他项目的 Hero 场景。

Master 当前只接受宽屏画布；不兼容画布明确报错。
场景资产使用前必须有准确字节、目标页和基准 Deck 的批准范围。裁剪、位置、透明度不改变原图字节。
图表数据、备注和原有科学对象保留可编辑性；栅格源图本身不会变成可编辑的数据图。

## 11. 机构模板优先级

`template-fill` 保留机构 Master/Layout、logo、页脚和强制占位符，不自动置换主题。
模板无法容纳所需内容时，需要明确的布局调整决定，不能静默转成另一模板。
Enhance 中保留的既有布局需要逐页有理由的 exception receipt；普通角色映射不能冒充实际布局检查。

## 12. Visual Quality Floor

Floor 核验六类页记录、实际组合观察、科学/语义/几何/字体 QA、全页预览、PDF、联系表、
资产批准、Art Direction 执行证据及人工审核。
视觉执行必须区分“声明了”“执行了”“在渲染中看到了”。缺失硬证据会阻断。
重复布局比例和卡片使用量是提示，不是数学审美标准。

## 13. Ambition、Anchor 与 STRETCH

full 对每页明确的 `ambition_context` 评估高价值组合机会。Anchor 是叙事作用，STRETCH 是改进建议，
不是要求每页加图或增加装饰。Floor 阻断不会被高 Ambition 覆盖。
`ambition_review_template.json` 绑定当前 Deck、渲染集和计划哈希；高价值页由人决定采用、保留或不采用。
审美分数与评价不由程序预填。

## 14. 内容感知插图决定

每页必须明确需要或不需要插图，真实科学图优先。
可导出的概念是受控类别，例如背景层次、研究流程、抽象框架、实施提示和连续性背景。
`illustration_context` 的受控概念、边界、焦点和留白必须来自获准计划，不能重读全文后随意改写。
full 的 `manual_illustration_records.json` 可作为下一步输入。没有请求记录不代表生成失败，也不意味着应该强制加图。

## 15. 非 API Manual Visual Asset Bridge

```powershell
$python = Join-Path $env:PPT_WORKFLOW_HOME '.venv\Scripts\python.exe'
$assetRoot = Join-Path $env:PPT_WORKSPACE_HOME 'visual-assets'
& $python -B -m scripts.academic_ppt.manual_image_handoff --manual-image-handoff --records $records --run-id $assetRun --asset-root $assetRoot --output $packetOutput --baseline $baselineDeck
```

上述路径变量由当前运行输出填写，`$assetRun` 使用新的唯一 run ID，输出目录必须不存在。
程序产生 Markdown/JSON 包和操作指南。人打开选择的图像界面，复制一个 prompt，生成 1–3 个候选并保存到本地。
不要把原始讲稿、病历、患者标识、项目路径、speaker notes 或 claim/source registry 粘入生成界面。
无法用受控概念表达时返回 `MANUAL_GENERATION_PACKET_UNSAFE`。

## 16. inbox、review、approval、approved_assets

文件放在 `<assetRoot>/candidate_inbox/<assetRun>/<asset_request_id>/`，
名称为 `<asset_request_id>__A.png`，也可 B/C。支持 PNG/JPEG/WebP；不接收任意 SVG/可执行内容。
只扫描明确授权的 inbox，检查路径、SHA256、真实格式、尺寸和文件完整性。

```powershell
& $python -B -m scripts.academic_ppt.manual_image_handoff --manual-image-handoff --import-image-candidates --package $packetOutput --asset-root $assetRoot --output $importOutput
```

`$importOutput` 必须位于 `<assetRoot>/candidate_runs/<assetRun>/<new-import-id>`。
自动生成本地候选比较 PPTX/PDF/联系表。它是标注 CANDIDATE / NOT APPROVED / PRESENTATION ONLY 的栅格 mockup；
科学权威仍是未修改的原生 baseline。文件存在不等于批准。

人工填写 `candidate_review_template.csv`。只有 `approve=true` 且 `decision=APPROVE` 才批准；
APPROVE_WITH_REFINEMENT、REJECT、NO_MEANINGFUL_GAIN、TOO_DECORATIVE、SEMANTIC_CONFUSION_RISK 不晋级。

```powershell
& $python -B -m scripts.academic_ppt.asset_approval --apply-approvals --import-root $importOutput --decisions $decisionCsv --approved-root $approvedOutput --reviewer $reviewer
& $python -B -m scripts.academic_ppt.asset_approval --assemble --source $baselineDeck --output $assembledDeck --registry $approvedRegistry --slide-ids $slideIdsJson
```

`$slideIdsJson` 是与 baseline 顺序完全一致的 ID 数组。批准记录冻结 baseline、图像、目标页与位置。
组装只允许空白获准区域内的原生 picture；覆盖既有科学对象会拒绝。原始候选 registry 仍保持 CANDIDATE。

## 17. 科学图与装饰图

科学图的数据、条件、统计含义和来源由人负责。装饰图固定为 `scientific_evidence=false`、
`presentation_only=true`，不能仿造病人、CT/MRI、EEG/ECG、监测曲线或统计发现。
图像内部不添加科学标签和数字，必要科学文字保留为原生 PowerPoint 文本。

## 18. 运行与重新审核

```powershell
& .\scripts\new_project.ps1 -ProjectId 'academic-demo' -Route generate -Quality validated -WorkspaceHome $env:PPT_WORKSPACE_HOME
$project = Join-Path $env:PPT_WORKSPACE_HOME 'projects\academic-demo'
& $python -B .\run_ppt_workflow.py --project $project --route generate --quality quick
& $python -B .\run_ppt_workflow.py --project $project --route generate --quality validated --visual-plan $visualPlan
& $python -B .\run_ppt_workflow.py --project $project --route generate --quality full --visual-plan $visualPlan
```

补齐科学材料、Brief 和批准的视觉计划之后运行后两条。首次缺计划、缺来源或缺人工复核而阻断是预期行为。
每次生成使用新运行目录。不要把命令成功退出等同于科学批准；检查 `VISUAL_DELIVERY_STATUS`。

已有获批候选组装后，不重新生成被审核的文件；重新渲染并验证科学不变性：

```powershell
& $python -B -m scripts.academic_ppt.visual_workflow --audit-assembly $assembledDeck --source-run $sourceEngineRun --output $newAuditRun
& $python -B -m scripts.academic_ppt.visual_workflow --review-run $engineRun --output $reviewedRun --visual-evidence $signedVisualEvidence --visual-plan $visualPlan
```

`$sourceEngineRun` / `$engineRun` 是含 `visual_review_context.json` 的完整运行目录，路径见项目 audit 中的 `visual_engine_location.json`。
重新审核不改 Deck 字节。signedVisualEvidence 需绑定 exact Deck SHA256，并引用实际逐页观察、资产授权和人工审核记录。
可以从 `visual_evidence/quality_manifest.json` 获取所需结构；不复制旧 Deck 的签名到新 Deck。
组装后的图像还必须在最终渲染中接受全页资产适配和科学/视觉复核；候选批准不会自动满足最终 Floor。

## 19. 输出与交付

普通用户查看 draft/final Deck、PDF、preview 联系表和 audit。
完整 engine run 保留 Deck IR、source manifest、QA 与 `visual_evidence`，供审计和精确复核使用。
`PASS` 才满足交付门禁；HUMAN_REVIEW 仍待人审；BLOCK 必须处理原因。
template-create 仅提供 profile，不标记 Deck Floor 通过。

## 20. Human Scientific Gate

逐页确认措辞、数字、单位、条件、否定词、数据来源、引文、备注和解释边界。
Q20 必须同时记录科学批准和视觉批准，并绑定 Deck、全部 slide IDs 与 render-set hash。
程序不会推断或代签；可追溯性检查不能替代科学判断。

## 21. Human Visual Gate

检查联系表和每页实际预览：可读性、视觉焦点、图表主次、版式重复、装饰必要性、位置和字号。
审核记录填写 reviewer、reviewed_at、status，以及当前 deck/render hashes。full 还须复核 Anchor/STRETCH 机会。
更改任何页或图像后，需要新渲染和对应审核，不能沿用过期批准。

## 22. Enhance

KEEP 保留页对象、备注、图表、关系与主题继承。变更需要明确 stable slide ID、section 或 figure selector，
以及 previous Deck IR；不能按页号猜测语义对象。validated/full 使用完整验证。
quick 可使用经过验证的 fast 增量缓存和显式 KEEP/REPLACE/INSERT_AFTER operation plan；
缺缓存、来源删除、科学定义变化或影响范围不明时必须完整验证。
此能力要求已经准备并批准的 changed-slide candidate，不能承诺自动完成科研内容重写。
实现与底层参数见 [架构说明](architecture.md) 和 [KEEP 合同](KEEP_语义保留合同.md)。

## 23. 隐私

患者资料、原始项目文件、候选、批准资产与运行输出保留在私有工作区，不能提交仓库或发布包。
style-only 不输出原文、备注、图表值或图像字节，不跟随 OOXML 外部关系。
隐私扫描检测路径、凭据特征和外部关系；图像中的患者标识、临床内容仍需人工检查。
任何网络图片生成均由人单独操作，软件不调用生成 API。

## 24. 常见状态

| 状态 | 处理 |
|---|---|
| INFORMATION_REQUIRED | 补充或人工确认来源/定义 |
| APPROVED_VISUAL_PLAN_REQUIRED | 根据同一 Deck IR 准备并审批视觉计划 |
| ACTUAL_COMPOSITION_NOT_VERIFIED | 提供真实渲染观察；不能仅填写 family 名称 |
| MASTER_BINDING_MISSING_OR_UNVERIFIED | 核对完整逐页绑定及当前 Deck 哈希 |
| ASSET_SLIDE_OR_BASELINE_SCOPE_MISMATCH | 回到正确基准和目标页，或重新人工授权 |
| HUMAN_REVIEW | 完成人工科学和视觉审核 |
| PowerPoint 打开/几何失败 | 修复文件或排版，再运行实际渲染验证 |

不要通过降低检查强度、伪造 PASS 或沿用其他项目的批准来消除错误。

## 25. 推荐标准流程

创建项目 → 放入来源 → 填 Brief → 人工批准 visual brief → 科学规划/处理 → 解决科学不确定性 →
批准源绑定的页面角色与视觉计划 → validated 检查 Floor → full 评估 Anchor 机会 →
必要时人工生成、入箱和批准图像 → 新 Deck 组装/审计 → 查看全部预览 → 科学与视觉 Human Gate → 交付。
不需要插图的页可以保持原生文字、图形、表和图表。

## 26. 当前限制与维护检查

第二个独立真实项目尚未验证；不能宣称跨领域泛化或数学审美保证。
新版 Master、审批和组合路径具有合成回归与真实 PowerPoint 技术验证，但不替代真实项目人审。
本机的另一个目录也不构成第二台设备验证。

维护者在 Git 检出的仓库根目录运行（测试套件会核对已跟踪的合成 fixture，因此需要 Git 文件索引）：

```powershell
& $python -B -m unittest discover -s tests -q
& $python -B .\scripts\build_release_bundle.py --output-root $externalReleaseDryRun
```

发布 dry run 必须在仓库外。检查发布清单、隐私和链接后再由所有者决定是否发布；这些命令不推送、不创建 Release。
